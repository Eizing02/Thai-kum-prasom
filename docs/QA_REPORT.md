# รายงานทดสอบเกมคำชนคำ

ทดสอบบน Windows วันที่ 18 พฤศจิกายน 2569 ด้วย Node.js 24 และ Chromium ของ Playwright ใช้ `npm run preview` ทดสอบผลจาก production build

## Phase 1–5

| ระยะ | สิ่งที่ตรวจ |
| --- | --- |
| 1 · Foundation | ติดตั้งและล็อก dependency ตั้ง Vite, React, strict TypeScript, Tailwind, ESLint และ CI รัน lint, typecheck, smoke test และ build |
| 2 · เกมเมาส์ | lint, typecheck และ build ผ่าน Unit 36 รายการ และ E2E 4 รายการผ่าน ครอบคลุมลากผิดและถูก เล่นครบห้าด่าน การ์ด WebGL คำอธิบายและ CSV |
| 3 · กล้อง | lint, typecheck, tests และ build ผ่าน เปิด MediaPipe ด้วยวิดีโอจำลองและอ่านค่าที่วัดจาก Worker CPU ได้ |
| 4 · เชื่อมการควบคุม | ทดสอบคลายนิ้ว/มือหาย การหยิบผ่านกล้องจำลอง การพัก เปลี่ยนเป็นเมาส์ สัมผัส ตรวจปฏิเสธสิทธิ์ ปรับการจัดการคลิกสัมผัสหลังลากบน Chromium |
| 5 · ส่งมอบ | รันชุดตรวจจาก production build ครบ ตรวจการแก้คลังคำและเวลาเกม รวมทั้งรีวิว Impeccable และภาพที่เรนเดอร์ |

## ผลคำสั่งชุดส่งมอบ

| คำสั่ง | ผล |
| --- | --- |
| `npm run lint` | ผ่าน |
| `npm run typecheck` | ผ่าน |
| `npm test` | 46 ผ่าน · 0 ล้มเหลว · 5 ไฟล์ |
| `npm run build` | ผ่าน · Vite แจ้งขนาดฉาก Three.js ที่โหลดแยกจากหน้าแรก ประมาณ 923 kB ก่อน gzip และ 244 kB หลัง gzip |
| `npm run test:e2e` เมื่อ `TWM_TEST_MODEL=1` | 15 ผ่าน · 0 ล้มเหลว รวมสองกรณี MediaPipe กับวิดีโอจำลอง ชุด CI ปกติข้ามสองกรณีที่ต้องโหลดโมเดลผ่านอินเทอร์เน็ต |
| `npm audit --omit=dev` | 0 รายการจาก dependency สำหรับรันแอป |

ชุดทดสอบตรวจคู่คำตั้งต้นทั้ง 30 คู่ การสลับลำดับและกรณีผิด ตัวสร้างด่าน 75 seed ต่อชุดหัวข้อและระดับ การล็อกคะแนนซ้ำ ตัวกรองเมื่อเวลาย้อนหรือซ้ำ ท่าบีบและการคืนการ์ดเมื่อมือหาย การคืนทรัพยากรเมื่อออกจากหน้า และการย้ายข้อมูลการตั้งค่า รุ่น E2E ตรวจลากเมาส์ต่อเนื่อง สัมผัสจาก Chromium emulation คีย์บอร์ด ทดสอบหมดเวลา JSON ไปกลับ CRUD คลังคำ CSV ปฏิเสธสิทธิ์และบันทึกรอบข้ามรีโหลด

`npm audit` แบบรวมเครื่องมือพัฒนาแสดง 12 รายการระดับสูงที่โยงกับ advisory ของ picomatch ใน dependency ทางอ้อม ตามข้อมูลวันที่ทดสอบยังไม่มีรุ่นแก้ไขที่เผยแพร่ ผลที่ deploy เป็นไฟล์ static จาก `dist` และ runtime bundle ไม่รวมเครื่องมือ lint, test หรือ Vite development server [ประกาศ GHSA-fc5q-39xc-vjpf](https://github.com/advisories/GHSA-fc5q-39xc-vjpf)

## รีวิว Impeccable 4.9.2

ตรวจ source CSS/TSX ด้วย detector ได้ 0 รายการหลัก และ 1 ข้อสังเกตเรื่องเส้นกริดสองแกนในภาพหน้าแรก เปลี่ยนเป็นกลุ่มจุดในสนามทดลองและตรวจภาพอีกครั้ง รีวิวจากภาพเรนเดอร์ที่ความกว้าง 1440, 390 และ 320 px ครอบคลุมหน้าแรก เลือกโหมด สนาม คำตอบ ผล คลังคำ และ diagnostics

| --- | --- |

| ประสิทธิภาพ | 3/4 · ฉาก WebGL โหลดแยกและใช้ DPR ตามคุณภาพ กล้องเริ่มเมื่อได้รับสิทธิ์ ยังมีไฟล์ Three.js ขนาดใหญ่บนการเข้าฉากครั้งแรก |
| ระบบภาพ | 3/4 · ใช้ฟอนต์ไทยในเครื่อง พร้อมสีครีม หมึก เหลืองและม่วงเป็นตัวแปรร่วม ภาพแม่เหล็กต้นฉบับใช้เฉดเฉพาะของชิ้นงาน |

การตรวจภาพรอบแรกพบว่าการ์ดยื่นเข้าหากันในระดับง่ายบนมือถือ ตัวเลือกปานกลางตัดคำ และบทนำหน้าครูมีคำหลงบรรทัด หลังแก้ ขอบปุ่มการ์ดห่างประมาณ 13 px ในระดับง่ายที่ 320 และ 390 px และอย่างน้อย 10.5 px ในระดับยากที่ตรวจ ตัดป้ายตกแต่งในสนามหลายคู่จอแคบเพื่อให้พื้นที่แถวแรก ส่วนภาพแม่เหล็กและลำดับเนื้อหาของกล่องคำตอบผ่านการตรวจภาพ

## กล้องและข้อจำกัด

- ใช้ Hand Landmarker จริงกับแหล่งภาพจำลองของ Chromium ผ่านทั้ง Worker CPU และ main-thread CPU ตรวจกรณีส่ง pose จำลองเข้า pipeline แล้วให้ท่าบีบลากการ์ดจริงจนขึ้นคำอธิบาย
- ตัวอย่างหนึ่งช่วงใน diagnostics กับวิดีโอจำลองวัดได้ประมาณ 20 FPS สำหรับกล้อง 12 FPS สำหรับอนุมาน และ 60 FPS สำหรับหน้าเว็บ ความหน่วงจากรับเฟรมถึงจัดการประมาณ 51 ms ตัวเลขเป็นค่าของรอบนั้นและขึ้นกับเครื่องกับความละเอียด
- ยังรอทดสอบกล้องกายภาพ ปริมาณแสง มือหลายมุม ความแม่นยำการหยิบ อัตราวางหลุด และ performance บนมือถือหรือ Safari จริง ใช้ขั้นตอนใน [คู่มือการตรวจกล้อง](HAND_TRACKING.md)
- โหมดกล้องต้องเข้าถึงแหล่ง WASM และโมเดลผ่านเครือข่ายครั้งแรก กลไกสำรองคือเมาส์ สัมผัส และคีย์บอร์ด การอ่านออกเสียงขึ้นกับเสียงไทยในเครื่อง

## ทดสอบซ้ำหลังปรับสนามกล้อง

วัดบน Windows ด้วย Chromium และ MediaPipe กับสตรีมกล้องจำลอง 640×480 ใช้ production build และหน้าต่าง 1440×900 เก็บช่วงละ 4.5 วินาทีหลังตัวตรวจจับมือพร้อม

| ค่าที่วัด | หน้าปรับเทียบก่อนแก้ | หน้าเกมก่อนแก้ | หน้าเกมหลังแก้ |
| --- | --- | --- | --- |
| เฟรมของหน้าเว็บโดยประมาณ | 60 FPS | 46 FPS | 60 FPS |
| เวลาเฟรมเปอร์เซ็นไทล์ที่ 95 | 16.8 ms | 33.4 ms | 16.7 ms |
| กรอบแสดงภาพกล้อง | 817×535 px | 1080×459 px | 1005×753 px |
| เรนเดอร์ WebGL พร้อมกล้อง | ปิด | เปิด | ปิด |

หลังแก้ ภาพและการ์ดใช้กรอบเดียวกันที่รักษาอัตราส่วน 4:3 ตรวจในจอเดสก์ท็อป มือถือแนวตั้ง และมือถือแนวนอน การทดสอบท่ามือจำลองผ่านเส้นทางกล้องยืนยันว่าการหน่วงผลตรวจหนึ่งเฟรม 700 ms ไม่ทำให้การ์ดหลุด และยังวางบนคำเป้าหมายได้เมื่อกลับมารับเฟรมตามปกติ ผล FPS เป็นของรอบวัดด้วยกล้องจำลอง เครื่องและกล้องที่จะใช้สอนต้องวัดแยก

ตรวจซ้ำผ่าน `lint`, `typecheck`, `build`, Vitest 47/47 และ Playwright 15/15 เมื่อเปิดการทดสอบโมเดลจริงกับสตรีมจำลอง

## ทดสอบซ้ำหลังปรับจังหวะลากและปล่อย

- Vitest ผ่าน 51/51 และ Playwright ผ่าน 15/15 รวม lint, typecheck และ production build ผ่าน
- การทดสอบในสนามจำลองเฟรมที่เริ่มคลายนิ้วบนคำถูก แล้วส่งพิกัดนอกเป้าในเฟรมถัดไป เกมยังเชื่อมคำเดิมครั้งเดียว ตรวจกรณีบีบกลับ มือหาย การวางผิดโดยไม่เพิ่มคะแนน และเมื่อ GPU Worker ค้างให้ลอง CPU Worker ก่อนด้วย
- ตรวจการวาดระหว่างลากโดยเปิดแอนิเมชันแล้ววัดจุดเล็งและจุดกึ่งกลางการ์ดในเฟรมที่พิกัดเปลี่ยน ระยะต่างต่ำกว่า 1 CSS px ในกรณีลากกลางสนามที่ทดสอบ
- วัด MediaPipe จริงใน Edge บน Windows โดยใช้วิดีโอจำลอง 640×480 ที่สร้างจากภาพมือเดียวกัน ช่วงละ 4.5 วินาทีหลังเริ่มประมวลผล ทั้งหน้าปรับเทียบและสนามใช้ Worker CPU แม้ตั้งกราฟิกเป็นระดับสูง
